## 一、选题背景、意义与需求

### Q1 为什么选择「健身人群饮食规划」这个题目？

**A：** 健身人群对蛋白质、热量与进餐结构敏感，通用饮食建议往往无法满足「增肌/减脂/维持」等目标与训练强度差异。本课题将健康档案、规则化标签与计划生成、菜谱推荐和执行反馈串成闭环，既有实际应用价值，也便于在工程上体现需求分析、系统设计与实现完整性。

### Q2 你的系统与通用健康管理类 App 有什么本质区别？

**A：** 通用产品多为记录与展示；本系统强调**面向健身场景的结构化档案（BMI、TDEE、目标、过敏原等）**、**可解释的规则化标签（Drools）**、**可执行的日/周饮食计划**以及**餐后反馈驱动的偏好微调**，把「规划—执行—反馈—调整」落在同一套业务链路里。

### Q3 系统的目标用户与角色是如何划分的？

**A：** 主要分为**普通用户**（维护档案、生成计划、浏览/收藏菜谱、提交反馈）与**管理员**（用户与内容治理、菜谱与计划类审核、规则与统计等）。技术实现上通过角色（如 USER/ADMIN）与 JWT 鉴权区分接口访问范围。

### Q4 你做了哪些需求分析？功能需求与非功能需求分别是什么？

**A：** 功能需求包括：注册登录、健康档案与体重曲线、饮食标签与计划生成、菜谱检索与推荐、执行反馈、管理后台（用户/菜谱/计划/规则/统计等）。非功能需求包括：可维护的分层架构、接口文档化（Swagger）、基本安全（认证授权、密码存储）、可扩展的规则与缓存、以及一定的性能与稳定性（缓存、限流、异常与日志）。

### Q5 「个性化」在系统里具体体现在哪里？

**A：** 至少三方面：① 健康档案与目标、过敏原等个体输入；② Drools 规则生成的**饮食标签**约束推荐与计划模式；③ 用户餐后反馈与偏好数据参与**后续推荐/参数微调**（本实现为规则与权重层面的轻量调整，而非复杂深度学习模型）。

### Q6 为什么强调「健身人群」而不是全体人群？

**A：** 健身人群的营养目标更明确（如增肌对蛋白质与总热量更敏感），训练强度与身体数据变化更频繁，对「可执行计划」和「反馈迭代」的需求更强；缩小领域有利于规则与数据结构落地，避免泛泛而谈。

## 二、总体架构与技术选型

### Q7 系统总体架构是怎样的？

**A：** **前后端分离**：浏览器端为 Vue3 + Vite 单页应用；服务端为 **Spring Boot 单体应用**，对内采用分层（Controller / Service / Mapper 等）与模块化包结构；数据层为 **MySQL**；**Redis** 用于缓存与部分限流等。

### Q8 【易追问】论文里若出现「微服务架构」，你实际部署是微服务吗？如何解释？

**A：** 当前实现是**一个 Spring Boot 进程 + 独立前端**，属于**前后端分离下的模块化单体（Modular Monolith）**，并非多服务独立部署的微服务集群。若论文已统一为「模块化单体、可演进到微服务」则与实现一致；答辩时可说明：毕设阶段优先保证业务闭环与可维护，微服务带来的运维复杂度较高，后续可按域拆分。

### Q9 为什么选择 Spring Boot？

**A：** 约定优于配置、生态成熟（Security、Validation、MyBatis-Plus、Redis、OpenAPI 等），适合快速构建 RESTful API 与统一异常处理；与 Drools、Flyway 等集成成本低，便于毕设按期交付。

### Q10 为什么前端选用 Vue3 + Vite？

**A：** Vue3 组合式 API 利于拆分业务逻辑；Vite 开发体验好、构建快；配合 Element Plus 可快速实现管理端与用户端界面，并支持响应式布局与 PWA 等扩展。

### Q11 前后端如何交互？跨域与 API 前缀如何处理？

**A：** 前端通过 HTTP 调用后端 REST 接口；开发环境通常在 Vite 配置**代理**将 `/api` 转发到后端，避免浏览器跨域问题；生产环境可由网关或 Web 服务器统一反向代理。

### Q12 【易追问】单体应用会不会成为性能瓶颈？

**A：** 单体并不等于性能差；瓶颈更多在数据库、缓存策略与热点接口。本系统对热门菜谱等使用 **Redis 缓存**，并对部分操作做限流；若用户规模上升，可水平扩展应用实例、读写分离、缓存分层，再考虑按域拆分服务。

## 三、数据库设计与持久层

### Q13 数据库选 MySQL 的理由？字符集与引擎如何选择？

**A：** MySQL 成熟稳定、与 Spring 生态集成好、运维成本低。建议使用 **utf8mb4** 以支持完整 Unicode（含 emoji），存储引擎 **InnoDB** 支持事务与外键，适合业务数据一致性要求。

### Q14 核心实体有哪些？它们之间的关系是什么？

**A：** 典型实体包括：`user`（用户）、`health_profile`（健康档案）、`diet_tag`（饮食标签）、`recipe`（菜谱）、`meal_plan`（饮食计划）、`feedback`（反馈）、`body_log`（体重日志）、`user_preference`（偏好）、`system_notification`（通知）等。关系上用户一对多档案/计划/反馈/日志，菜谱与计划、反馈之间通过外键或用户维度关联（具体以 ER 图与表结构为准）。

### Q15 数据库版本如何管理？

**A：** 使用 **Flyway** 迁移脚本（`db/migration`，当前为 `V1__init_schema.sql`），保证环境间表结构可追溯；手工可从项目根执行 `database/schema.sql`（内部加载同一 V1 文件）完成一次性初始化。

### Q16 【易追问】论文中的表数量、字段数与 ER 图不一致怎么办？

**A：** 答辩前应做「三层对照」：**实体图 → ER 图 → 物理表 + 代码实体类**，统一字段命名与个数；若终稿已删减或合并表，图表必须同步更新。回答时说明：以当前代码与 `V1__init_schema.sql`（或 Flyway 生效库）为准，论文图表已对齐终稿。

### Q17 为什么对菜谱、计划等做「审核」设计？

**A：** UGC 菜谱与计划内容存在合规与质量风险；审核流（待审/通过/驳回）可把**内容安全与质量控制**纳入系统管理闭环，并支撑管理员运营。

## 四、安全机制与权限

### Q18 用户认证方案是什么？为什么用 JWT？

**A：** 采用 **JWT**（access + refresh 的常见实践）实现**无状态认证**：服务端不必集中存储会话，易于水平扩展；配合 HTTPS 与较短 access 有效期可降低令牌泄露风险（具体以你的实现为准）。

### Q19 密码如何存储？能否明文？

**A：** **不能明文**。应使用 **BCrypt** 等单向哈希加盐存储；登录时对用户输入做相同哈希比对。

### Q20 Spring Security 在项目中起什么作用？

**A：** 配置安全过滤器链、无资源访问规则、集成 JWT 过滤器完成**身份认证与授权**；对管理端与用户端接口做角色区分。

### Q21 如何防止常见 Web 攻击？

**A：** ① **SQL 注入**：使用参数化查询/MyBatis 绑定参数，避免字符串拼接 SQL；② **XSS**：前后端对用户输入做转义与内容策略控制（富文本场景更需谨慎）；③ **越权**：服务端以用户 ID/角色校验资源归属，不只信任前端传参；④ **CSRF**：无状态 API 常配合 Token；若使用 Cookie 需额外防护。可补充：曾用 ZAP 等做基线扫描作为实验证据（若有）。

### Q22 【易追问】JWT 被盗用了怎么办？

**A：** 缩短 access 有效期、使用 refresh 轮换、HTTPS 传输、关键操作二次验证（视产品要求）；服务端可维护黑名单或版本号机制吊销令牌（实现深度因项目而异，回答到原则即可）。

## 五、核心业务：健康档案与营养计算

### Q23 BMI 如何计算？分级依据是什么？

**A：** \( \text{BMI} = \frac{\text{体重(kg)}}{\text{身高(m)}^2} \)。分级通常按中国成人标准：偏瘦/正常/偏胖/肥胖等区间（具体阈值以论文与实现代码一致为准）。

### Q24 TDEE 用什么公式？为什么选它？

**A：** 常见实现采用 **Mifflin-St Jeor 公式**估算基础代谢（BMR），再乘以**活动系数**得到 TDEE。该公式在一般人群中应用广泛、可解释性强，适合作为工程化默认值；若用户有更专业需求，可在「展望」中写接入个体化实测数据。

### Q25 健康档案里哪些字段影响计划与推荐？

**A：** 典型包括：身高体重、性别年龄、健身目标、过敏原、活动水平等；它们进入规则引擎生成**饮食标签**，并影响菜谱筛选与热量/营养素结构建议。

## 六、Drools 规则引擎与「可解释性」

### Q26 为什么引入 Drools？不用 if-else 可以吗？

**A：** 规则多且会变时，if-else 难以维护且易漏测。Drools 把**业务规则外置为规则文件（.drl）**，便于阅读、测试与迭代；也便于向答辩老师展示「可解释的规则链」。

### Q27 规则大致包含哪些类型？

**A：** 例如：根据 BMI 判「低卡」需求；增肌目标对应「高蛋白/高热量」倾向；过敏原约束「无乳制品」等；以及结合运动强度/目标的复合规则（以 `diet-label-rules.drl` 与论文描述为准）。

### Q28 【易追问】规则冲突时谁优先？如何保证不矛盾？

**A：** 可说明：通过**规则优先级（salience）**、**议程组**或拆分规则包，并在测试用例中覆盖典型组合；上线前用固定样例用户档案做回归验证。

### Q29 规则能否热更新？如何实现？

**A：** 若项目支持从指定目录加载规则文件，可在不重启的情况下**重新加载 Kie 容器**（实现细节因 `DroolsConfig` 与部署方式而异）。答辩可强调工程价值：规则变更不必改 Java 核心代码即可调整策略。

## 七、饮食计划生成与执行

### Q30 计划生成是算法还是规则？流程是什么？

**A：** 整体是**在标签与目标约束下的计划生成逻辑**：结合 TDEE 与餐次分配比例（如早午晚热量占比），从菜谱库中筛选匹配菜品并组合为日计划；实现上可能同时用到服务层逻辑与 Drools/规则输出建议（以论文中的流程图与 `MealPlanRuleService` 为准）。

### Q31 日计划与周计划有什么区别？

**A：** 日计划细化到餐次与菜品；周计划强调连续多天的结构安排与多样性/重复控制（若已实现）。以你论文与界面为准说明。

### Q32 「替换菜品、跳过、外食」业务意义是什么？

**A：** 提高**可执行性**：真实生活中用户会外食或临时替换；系统记录这些状态有利于反馈分析与后续推荐修正。

### Q33 【易追问】计划会不会生成不合理组合（如营养素失衡）？

**A：** 说明当前版本的约束条件：热量区间、标签匹配、简单营养素汇总等；承认复杂医学营养干预需专业医师；未来可加强营养素下限/上限与多样性惩罚等。

## 八、菜谱检索、推荐与缓存

### Q34 菜谱推荐的大致思路？

**A：** 在过滤过敏原与标签匹配后，对候选菜谱做评分排序；项目中可采用**多特征加权**与**余弦相似度**等融合方式（以论文与 `IRecipeService` 实现为准）。

### Q35 余弦相似度用在什么地方？向量是什么？

**A：** 将菜谱与用户偏好等表示为向量空间中的特征向量，用余弦相似度衡量方向一致性；具体维度可为标签、营养素、品类等（与实现一致即可）。

### Q36 为什么用 Redis 缓存热门菜谱？

**A：** 热门列表访问频率高，缓存可降低数据库压力、缩短响应时间；可配合**定时任务**刷新，平衡实时性与负载。

### Q37 【易追问】缓存与数据库不一致怎么办？

**A：** 采用 TTL 过期、主动刷新接口、或在菜谱审核通过/更新时失效相关 key；承认强一致场景需更复杂方案，本系统以**最终一致**可接受为前提。

## 十三、创新点、难点与不足

### Q61 【§1.1 研究背景 vs §1.4 研究内容】前文强调「前后端分离 + 模块化单体」，后文又写架构搭建「融入微服务的设计思路」并形成 E-R 图——你到底是单体还是微服务？这是不是前后矛盾？
